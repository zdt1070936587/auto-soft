## 1. 阶段目标

阶段 2 做出「提前引入的能力」：元数据仓库 + 动态 DDL + 通用 CRUD + 前端 Schema 渲染。阶段 3 的 Agent 只准调用这些能力，不准执行任意 SQL。

必须同时满足：

1. 开发者（或超管）可在后台维护 app / 实体 / 字段 / 页面 schema，无需改代码发版。
2. 发布后自动建 `dyn_{appCode}_{entityCode}` 表（仅允许此前缀），并写入 `sys_menu`、授权给指定角色。
3. 通用运行时接口完成分页、详情、新增、修改、逻辑删除；列名与排序只来自白名单。
4. 前端动态路由 `/app/:app/:entity`，`SchemaRenderer` 按 JSON 渲染表格与表单。
5. 改草稿 schema 再发布（或刷新预览）后页面立刻变化。
6. Controller 零业务；DDL 与动态 SQL 全部在 Manager，且禁止拼接未校验标识符。

## 4. 核心约定

| 项 | 规则 |
| --- | --- |
| appCode / entityCode / fieldCode | `^[a-z][a-z0-9_]{1,30}$`，发布后 **code 不可改** |
| 物理表名 | `dyn_{appCode}_{entityCode}`，生成前再校验一次正则 |
| 系统列（自动加，禁止元数据重复定义） | `id, created_by, created_at, updated_by, updated_at, deleted, flow_status` |
| `flow_status` | 阶段 2 默认 `none`；阶段 4 才启用流转 |
| 字段类型白名单 | `string, text, int, long, decimal, bool, date, datetime, dict, ref` |
| app 状态 | `DRAFT` / `PUBLISHED`（可另存 `version` 整数，每次发布 +1） |
| 权限码 | `app:{appCode}:{entityCode}:list\|create\|update\|delete` |
| SQL 标识符 | 仅引用元数据中已存在的 code，用双引号包裹 PostgreSQL 标识符；**禁止**把请求参数直接拼进列名 |

类型映射：

| 元类型 | PostgreSQL |
| --- | --- |
| string | `VARCHAR(n)`，n 默认 255，最大 1024 |
| text | `TEXT` |
| int | `INTEGER` |
| long | `BIGINT` |
| decimal | `NUMERIC(18,2)` |
| bool | `SMALLINT`（0/1） |
| date | `DATE` |
| datetime | `TIMESTAMPTZ` |
| dict | `VARCHAR(64)`，选项在字段 `options_json` |
| ref | `BIGINT`，`ref_app` + `ref_entity` 指向另一实体（阶段 2 表单用下拉，列表显示 id 即可） |

## 7. 后端设计

### 7.1 DdlManager（framework 级风险点）

步骤化：

1. `assertSafeTableName(app, entity)`
2. `buildColumnDdl(fields)`（类型白名单 switch，禁止拼接 field_type 原文）
3. `CREATE TABLE IF NOT EXISTS ...` 含系统列
4. 增量：新字段 `ALTER TABLE ... ADD COLUMN`（只 add，不 drop）

所有 SQL 用 `JdbcTemplate` + 预编译；**表名列名不是绑定参数**，必须来自白名单函数 `quoteIdent(code)`。

事务：元数据提交与 DDL 同一事务；DDL 在 PostgreSQL 上部分不可回滚，失败要记日志并拒绝发布。策略：先写元数据 DRAFT，发布时再 DDL；DDL 失败则 status 仍 DRAFT 并返回明确错误。

### 7.2 RuntimeSqlManager

- SELECT 列 = 系统列 ∪ listed 字段
- WHERE：仅 `queryable` 字段；string 用 `LIKE` 且参数绑定；禁止 `%` 由服务端乱拼导致全表（用户输入作 bind 值）
- ORDER BY：仅允许 `id` 或 listed 字段 code，方向只允许 `ASC`/`DESC`
- 始终 `deleted = 0`
- insert/update 只写元数据中的业务列 + 审计列；忽略请求体多余键

### 7.3 PublishService.main 步骤

1. 校验 app 至少 1 个实体、每实体至少 1 个业务字段  
2. 对每个实体 `DdlManager.ensureTable`  
3. 为每个实体 upsert `sys_menu`（path=`/app/{app}/{entity}`）  
4. 为勾选角色写 `sys_role_menu` 及按钮权限码  
5. 更新 `meta_app.status=PUBLISHED`, `version+1`  
6. 写 `meta_app_menu`

下架（可选，阶段 2 建议做「取消发布」）：菜单 `visible=0`，**不删表、不删数据**。

### 7.4 API

权限：建模接口 `meta:app:manage`（仅 SUPER_ADMIN、DEVELOPER）。运行时按 `app:...` 权限码。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST/PUT/DELETE | `/api/meta/apps` 及 `/{id}` | app CRUD |
| GET/POST/PUT/DELETE | `/api/meta/apps/{appId}/entities` | 实体 |
| GET/POST/PUT | `/api/meta/entities/{id}/fields` | 字段（删除=软删） |
| PUT | `/api/meta/entities/{id}/pages/{type}` | 保存 schema_json |
| POST | `/api/meta/apps/{id}/publish` | 发布 |
| GET | `/api/meta/apps/{id}/schema` | 供预览：实体+字段+page |
| GET | `/api/runtime/{app}/{entity}/page` | 分页 |
| GET | `/api/runtime/{app}/{entity}/{id}` | 详情 |
| POST | `/api/runtime/{app}/{entity}` | 新增 |
| PUT | `/api/runtime/{app}/{entity}/{id}` | 修改 |
| DELETE | `/api/runtime/{app}/{entity}/{id}` | 逻辑删 |
| GET | `/api/runtime/{app}/{entity}/schema` | 前端渲染用 schema（已发布或预览 token） |

预览：未发布 app 仅 DEVELOPER 可带 `?preview=1` 读 schema 和空数据，不暴露给 USER。

`RuntimeController` 只调 `RuntimeService`；内部步骤：解析 app/entity → 加载元数据缓存 → 校验权限 → 调 SqlManager。

元数据缓存：本地 Caffeine 或 Map，发布时失效。阶段 2 用 Spring Cache 简单实现即可。

## 8. 前端设计

### 8.1 应用建模页（`/meta/apps`）

左：app 列表；中：实体与字段表格（类型下拉、是否查询/列表/必填）；右或抽屉：JSON schema 可先不做可视化编辑，用表单生成默认 LIST/FORM。

按钮「发布」：确认角色（默认 USER）后调用 publish。

### 8.2 SchemaRenderer

- LIST：`a-table` + 查询区（queryable 字段）+ 新增 + 编辑弹窗 + 删除
- FORM：按 field_type 映射 `a-input` / `a-textarea` / `a-input-number` / `a-switch` / `a-date-picker` / `a-select`
- 校验：required、string 长度

动态路由：登录后 `menus` 里 path 匹配 `/app/:app/:entity` 的注册到同一 `RuntimePageView`。

### 8.3 工作台

可放「已发布应用」入口卡片，避免 USER 不知道点哪。
